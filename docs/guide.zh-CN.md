## 交付目录速览

默认资料根目录为用户主目录下的 `~/Aimship/`，安装时另有配置则沿用。**每次交付在该根目录下独立存放，以 AI 回执中的实际路径为准**；需要另存时请明确说明。

在 AI 工具项目空间中开展交付，空间中同时访问原有材料和 Aimship 交付目录：

```text
AI 工具项目空间
├── 用户已有项目材料（按实际情况提供，保留原位置）
│   ├── 原型、PRD、其他参考文档（如已有）
│   └── 项目代码（如已有）
└── Aimship 初始化生成的本次需求交付目录
    └── 添加原目录 → ~/Aimship/20261027-login-signup/
```

按下方[启用并提出诉求](#guide-setup)完成初始化，收到实际路径后，将该交付文件夹（本例为 `20261027-login-signup`）添加到当前 AI 工具项目空间，或授予该目录的访问权限，后续在这个空间继续交付。已有项目材料按需要提供访问，不由 Aimship 初始化创建。目录名仅为示例，无需提前手工创建，也不要复制整份交付或在项目空间另建一套。

该交付目录中的材料如下：

```text
~/Aimship/                         # 资料根目录
└── 20261027-login-signup/          # 示例交付目录
    ├── status.md                  # 当前工作、待审材料、下一步
    ├── source/request.md          # 原始诉求
    ├── prd.md                     # 需求与验收标准
    ├── prototype/index.html       # 页面交互原型
    ├── tech-design.md             # 技术方案
    ├── openapi.yaml               # HTTP 接口契约
    ├── database.sql               # 本例单数据库变更
    ├── testing.md                 # 用例与后续执行结果
    ├── plan.md                    # 实施任务与进度
    ├── review.md                  # 各批及整体审查
    └── handoff.md                 # 成果与交接说明
```

这些材料逐步形成，按需保留。正文中的 REQ、AC、TC 等编号可直接搜索，跨文档沿用对应编号，不要求锚点跳转。外部权威需求由 `scope.md` 承接，重要变更记入 `change-log.md`，独立调查才使用 `diagnosis.md`。查看进度先打开 `status.md`；需求修改或验收意见直接告诉 AI。

## 1. Aimship 使用示例

以登录注册功能演示从需求到验收。**这是虚构实践参考，措辞和业务方案无需照抄。** 本例稍后提供工程和隔离测试数据库，约定需求后确认原型，再做技术设计；实际原型安排按交付需要确定。

同一会话沿用一个 Aimship 入口，批准后按安排继续，无需逐阶段调用。需要你审核时，AI 会逐份展示材料并等待明确结论；修改后重新送审。

### 1.1 启用并提出诉求

**用户操作**：明确使用 Aimship，并说明目标。例如：

> 使用 Aimship，做用户名密码注册、登录、退出和登录后首页。完成开发与本地验证，不部署；代码稍后提供。

已有原型、PRD 或其他文档时，提供原位置即可，原件保留，用户无需手动复制。AI 按来源规则将正式采用的版本及必要依赖资源留存为本次交付 `source/` 中的副本，并记录采用依据；仅作背景参考的材料无需全量复制。后续修改先明确编辑对象，新版不覆盖旧依据。

**AI 处理**：确定交付目录并核对访问，保留诉求，建立或续接交付，告知实际保存目录、当前工作和下一步。若无法访问，提示你添加该原目录或授权；不会改存到项目空间。

**输出产物**：`source/request.md` 保存原话；`status.md` 显示进度。新建交付时，AI 优先按明确偏好，否则按当前交流语言保存本次交付语言；状态和新文档沿用，文件名、编号、来源原文及已有文档不变。

### 1.2 确认需求

**用户操作**：按已有材料提供输入。

- 没有 PRD／原型：说明功能和预期行为，如“用户名不能重复，退出后再进首页必须登录”。
- 已有材料：给出 PRD／原型的位置、版本和本次采用范围；只有部分材料也直接说明。

分别打开送审的需求文档和适用原型，核对范围、验收标准及页面行为。每次对当前一份明确通过，或指出要修改的内容。

**AI 处理**：澄清缺口；外部权威原件保留，覆盖充分的原型复用。无材料时先写需求，批准后按本例安排制作所需原型；无交互变化则不新增。逐份自检、送审，批准后保存再继续。

**输出产物**：`prd.md` 说明需求与验收标准，或 `scope.md` 记录外部材料的采用范围；本例新建 `prototype/index.html` 展示页面与反馈状态。原型不代表认证已实现，未实际检查的交互仍标明未验证。

<a id="guide-session-example"></a>

**换会话示例**：本例需求与原型通过并保存后，停止旧会话写入，在新会话明确启用：

> 使用 Aimship 继续「实际交付目录」的登录注册交付，先读取状态、已批准材料和待审核停点。

AI 重新核对同一交付目录的访问，读取状态并确认下一步技术设计；若仍有待审材料就停在那里，不重建或要求重述全部背景。也可留在原会话继续。

<a id="guide-design"></a>
<a id="14-审核技术方案"></a>

### 1.3 审核技术方案

**用户操作**：提供工程位置及已知测试条件；打开方案，检查密码保护、登录状态、访问控制和数据变更，明确通过或反馈。

**AI 处理**：读取工程，核对技术条件，设计实现方式及风险处理；缺少关键事实先补齐，方案批准后准备接口与 SQL。

**输出产物**：`tech-design.md` 说明怎样实现及取舍。此时设计后续 SQL，不要求 SQL 文件已经完成。

<a id="guide-contracts"></a>
<a id="15-逐份审核接口与-sql"></a>

### 1.4 逐份审核接口与 SQL

**用户操作**：接口送审时检查请求、响应、错误与登录要求；SQL 送审时检查目标库、结构、变更顺序及执行条件，分别通过或要求修改。

**AI 处理**：依据已批准方案准备适用文档，逐份自检并等待审核；全部通过后进入测试设计。已有权威契约复用，无对应变更不生成文件，多数据库分别提供 SQL。

**输出产物**：本例 `openapi.yaml` 约定 HTTP 接口，`database.sql` 描述单库变更。**文档批准不授权执行 SQL 或修改迁移机制。**

<a id="guide-cases"></a>
<a id="16-审核测试用例"></a>

### 1.5 审核测试用例

**用户操作**：打开用例，核对正常注册登录、重复用户名、错误密码、未登录访问及退出后访问的预期结果；通过或指出遗漏。

**AI 处理**：将验收标准转为可检查的用例，注明环境与覆盖范围；用例批准后制定实施计划。

**输出产物**：`testing.md` 的用例部分。这时还没有测试执行结果。

<a id="guide-plan"></a>
<a id="17-审核实施计划"></a>

### 1.6 审核实施计划

**用户操作**：打开计划，核对改动范围、任务依赖、分批与验证安排；通过或反馈。

**AI 处理**：按工程依赖拆任务，如先完成认证与会话，再接页面和访问限制，安排测试代码及审查；计划与必要文档批准后才实施，单批也需要计划。

**输出产物**：`plan.md` 说明各批做什么、依赖什么、如何检查。

<a id="guide-implement"></a>
<a id="18-分批实施与批内-review"></a>

### 1.7 分批实施与批内 review

**用户操作**：查看改动和进度，有偏离及时指出，如“注册成功后的跳转与原型不一致”。无需逐条批准执行日志。

**AI 处理**：按计划写代码，每批完成后审查并处理阻碍推进的问题，再进入下一批。全部批次完成后做整体审查，再统一验证；需求变化回到相应审核。

**输出产物**：工程代码；`plan.md` 追加执行进度，`review.md` 记录本批问题与修复。

<a id="guide-overall"></a>
<a id="19-整体-review"></a>

### 1.8 整体 review

**用户操作**：查看整体结论和遗留问题，必要时指出遗漏；不需要为每条审查记录另做文档批准。

**AI 处理**：检查全部实际改动及注册、登录、退出、首页访问的跨批衔接，处理阻碍验证的问题后进入独立验证。单批可用一份 review 明确覆盖批内及整体范围。

**输出产物**：`review.md` 追加整体审查结论。代码审查不能代替运行测试。

<a id="guide-verify"></a>
<a id="110-执行验证并处理失败"></a>

### 1.9 执行验证并处理失败

**用户操作**：提供约定的隔离测试环境，查看执行结果，补充复现信息或缺失条件；另需授权的操作先明确目标与动作。

**AI 处理**：对已 review 的代码执行用例，分别记录通过、失败、未执行。缺陷修复后审查并复测，保留失败历史；需求或设计问题回到相应材料。

**输出产物**：同一 `testing.md` 追加实际代码、环境、结果与证据。缺少必要验证时如实列出，不写成通过。

### 1.10 查看成果并验收

**用户操作**：按交接说明检查功能，符合目标后明确“验收通过”；有差异就说明实际与预期。

**AI 处理**：汇总成果与遗留事项，记录你的实际验收决定。完整交付需有必要文档批准、批内及整体 review、独立验证和最终验收依据。

**输出产物**：`handoff.md` 提供成果位置、用法、验证结论和合并／部署状态。先前文档批准不替代最终验收，开发完成也不等于已部署。

### 2.1 何时换会话

按 `status.md` 的建议在需求、技术与适用契约、用例、计划、实施批次、整体 review、验证批次之间换会话，也可继续当前会话；分组不改变逐份审核。

新会话操作见[演示中的续接示例](#guide-session-example)。同一交付只保留一个写入会话；可信记录可直接定位，找不到或有多个候选才询问。交付语言沿用已保存设置。首次保存前就要切换时，携带未保存诉求、计划位置及未完成操作。

### 2.2 中断后恢复

提供原交付目录、中断时的操作和错误信息。AI 核对已保存状态、文件与未完成操作，保留身份及资料；状态已保存但进度页失败时只修复缺失视图。重复启用不重新初始化。

进度页手改内容先保留，冲突先协调；不要靠改进度页表达批准。工程搬迁后提供新位置，由 AI 核对身份再更新关联。

### 3.1 已有资料或讨论

提供 PRD、原型或截图的位置、版本和本次使用范围，AI 按[确认需求](#guide-requirements)核对。若要直接维护已有 PRD，请明确说明；AI 核对本次目标和完成范围后送审，已有文件不等于已批准。

已有讨论可说：“使用 Aimship 继续刚才讨论的需求。”AI 整理可见的诉求、决定和待确认问题；看不到的历史请补充，建议不算批准。

### 3.2 修改已批准内容

说明改什么、为什么改、哪些保持不变；自行改过文档时指出文件。AI 在 `change-log.md` 记录重要变化，将受影响文档重新送审，相关工作待确认后继续。未受影响的工作、旧批准和测试历史保留。

新诉求写入需求文档和变更记录，不覆盖 `source/request.md`。原始诉求被误改时，从可靠原件恢复；找不到就暂停核对。错字或排版无需全部重审。交付后的小修可继续原交付；新目标或大幅重设计另建交付，并注明与原交付的关系。

<a id="guide-limits"></a>
<a id="27-只做到部分目标"></a>

### 3.3 只完成部分目标

本次只需需求、设计或明确不做测试时，请说明。AI 记录做到哪里及未覆盖的部分，交接时标明阶段性成果，未测试不写成通过。“先看预览”不会改变原定目标。

独立调查才使用 `diagnosis.md`；普通调试不增加调查阶段。

### 4.1 关联代码、修复或重构

提供代码目录，例如：“代码在「工程目录」，继续当前交付。”AI 沿用原交付目录和审核记录，需要了解现有功能时可先只读查看；实际修改仍按约定范围进行。新发现影响已批准内容时重新送审。远端地址不会触发自动克隆或搬迁。

修复缺陷时，提供预期表现、实际问题、复现步骤或日志。重构时，说明改善目标和必须保持不变的功能行为。

### 4.2 同时处理多个需求

每个需求使用独立交付目录，并说明共用的代码、接口、数据库或环境。可以同时分析；修改同一份代码时安排先后，或使用独立工作目录并安排合并。

AI 只能核对已知且可访问的交付，不会自动锁定或调度其他会话。请说明其他正在进行的修改，各自完成后仍需检查合并结果。

### 5.1 目录无法访问

按 AI 报出的实际路径，在 AI 工具中添加原交付目录或授予所需权限。若目录尚未创建，按工具支持的方式授权所需父目录，再继续初始化。不要复制交付或换个位置另建一套。

能读文件不代表能保存；AI 应根据实际读写结果报告是否成功。Aimship 不会替你操作权限界面。尚未保存的诉求请保留在当前会话，恢复访问后先核对已有文件，再继续；安装不会自动创建交付目录或授予访问权限。

### 5.2 找不到 Aimship 入口

先按 README 检查安装状态，再尝试新开会话或刷新 AI 工具的 Skill 列表，明确选择 Aimship。具体入口以所用 AI 工具的版本和支持方式为准；安装检查通过不代表它已经加载 Skill。

出现重复入口时，先核对来源和版本，保留已有定制内容。Codex 与 Cursor 共用安装入口，不要直接删除重复项。真实 AI 工具的发现、权限和跨工具续接尚未完整验证；可参考 [Cursor 文档](https://cursor.com/docs/skills)和 [Codex Skill 位置说明](https://learn.chatgpt.com/docs/build-skills)。

### 5.3 升级后继续

升级前保存当前工作，再按 README [升级](../README.zh-CN.md#update)。升级后重新启用 Aimship，核对实际绑定版本和交付状态；安装本身不会更新交付记录。

使用普通 Markdown 和可搜索编号记录交付。规则更新前核对影响，保留实际审批和测试记录，不补造结果。

### 5.4 安装维护与反馈

安装、升级、添加 AI 工具、版本与健康查询见 [README](../README.zh-CN.md#update)，移除见[卸载说明](../README.zh-CN.md#uninstall)。健康查询只检查安装文件和配置，不会修复交付文档；安装中断或文件缺失时，按 README 对应问题处理，不盲目重装。
