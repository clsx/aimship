## 1. 开始与推进

<a id="install"></a>
开始前，按 README 的[安装说明](../README.zh-CN.md#install)为所用 AI 工具安装 Aimship。安装需要 Node.js 22+ 和 npm；AI 工具需已登录并有可用模型。

<a id="准备工作位置"></a>
### 1.1 准备工作位置

- **已有工程**：复用当前可访问的项目空间，代码保留在原位置。
- **尚无代码**：可以先整理需求，无需创建代码仓库；选择可用于保存交付资料的工作位置。

交付资料默认放在 `~/Aimship/` 下，每次交付使用独立目录；安装时已配置其他位置的，沿用该配置。资料目录与代码目录分开。可在描述需求时指定资料位置，Agent 会核对并告知本次交付的实际目录。

安装不会自动创建交付资料或授予目录权限。若目标目录尚不存在或当前会话无法访问，Agent 会给出具体路径和操作：按所用 AI 工具的实际方式打开已有父目录，或创建并打开目标目录，再提供必要访问。已有可用空间直接复用。

### 1.2 启用 Aimship 并说明需求

安装后开启新会话，使用对应入口明确选择 Aimship：

| AI 工具 | 如何选择 | 未显示时 |
| --- | --- | --- |
| Codex | 在 Skill 选择器中选择 Aimship；CLI 中使用 `$aimship` | 新建会话或重启 CLI，列表未刷新时重启应用 |
| Cursor | 使用 `/aimship` | 新建 Agent 会话，检查 Customize → Skills；列表未刷新时重启 Cursor |
| Claude Code | 使用 `/aimship` | 新建会话并检查斜杠命令列表；列表未刷新时重启 Claude Code |

选择入口后，说明具体问题、期望变化和已知限制。也可以在请求中明确表达“使用 Aimship”；实际加载仍取决于 AI 工具是否已发现安装入口。

<a id="尚未形成需求文档"></a>

> 使用 Aimship 增加按当前筛选条件导出订单的功能，先确认导出字段，代码稍后准备。

完整 PRD、代码和全部技术条件都不是开始的前提。如果只有“做一个订单系统”这样的方向，Agent 会先澄清实际问题。已知材料可一并提供，未确定的交付终点和技术条件会保留为待明确事项。

<a id="确认保存结果并回答必要问题"></a>
### 1.3 确认保存结果并回答必要问题

保存后，Agent 会报告：

- 实际交付目录及 `status.md` 入口；
- 已保存的诉求、当前阶段或工作；
- 下一步需要补充的信息或将开展的工作。

回执也会说明所用 Aimship 版本及代码关联情况。原始诉求保存在 `source/request.md`；正式需求形成草稿后，再提供 `prd.md` 或采用已有材料的 `scope.md`。若暂时无法保存，Agent 会说明原因与所需操作。

继续回答影响本次范围和验收的问题。例如补充“导出订单号、金额和状态，保持当前筛选与排序”。需求文档完成后，按下一节打开文档并审核；初始化保存不代表需求已获批准。

<a id="阅读文档并给出结论"></a>
### 1.4 阅读文档并给出结论

每份需人审文档经 Agent 自检后，会附上当前状态、文档入口和审核重点。打开文档，重点确认目标、范围、验收标准及需要你决定的取舍。

认可当前版本时，可以明确回复：

> 这份需求文档通过。

需要调整时，直接指出内容：

> 导出范围还应包含状态为空的订单，请补充验收标准后再给我审核。

Agent 修订、自检后重新送审。重要的业务、范围、兼容性、成本或数据决策由你确认；授权内的日常技术取舍由 Agent 处理。讨论和待决问题保留原审核停点。

<a id="批准后继续推进"></a>
### 1.5 批准后继续推进

明确通过后，Agent 保存对应文档版本的批准、进度和下一步。同一建议会话组内直接继续；到组间边界，说明已完成内容并提供[新会话续接入口](#continue)。希望留在当前会话时，回复“在当前会话继续”即可。

标准主线是需求和验收标准 → 技术设计及适用的接口／SQL／交互产物 → 测试用例 → 实施计划 → 分批实施（含批内 review）→ 整体 review → 测试验证 → 交付验收。Agent 组织这条主线，按实际需要生成文档；已有材料需核对采用并完成相应审核。

review 或测试发现问题时，Agent 在授权范围内修复、复审或复测。新增实质决定和生产动作仍需对应授权。若明确排除测试用例和测试，Agent 会说明并记录范围，完成授权工作后交接未测试的阶段性成果。

### 1.6 已批准的需求发生变化

说明发生了什么变化、原因以及希望保留的内容。如果已修改正式文档，指出位置，让 Agent 核对修改的含义。

Agent 会分析对范围、设计、实现和验证的影响，记录决定，更新受影响的工作安排和文档。需要你判断的取舍会提出，其他授权内工作继续，原始采用资料继续保留。

已批准文档发生实质变更时，回到对应阶段重审，依赖它的工作等待审核解决后再继续；旧批准和结果保留为历史，不能用旧批准放行新版。重审通过后，按依赖顺序恢复。无关工作不重置，排版和错字修正不需全量重审。

重要变化及影响记录在 `change-log.md`，后续安排从 `status.md` 查看。不要通过修改 `status.md` 来改变需求或表示验收；它是生成视图，已有手改内容需先保留，再由 Agent 核对和重建。

## 2. 会话、进度与验收

<a id="安排新会话与交接"></a>
<a id="在新会话中接续"></a>
### 2.1 在新会话中接续

1. 等当前会话确认文档、批准和进度已保存，并停止写入。
2. 在 AI 工具中新建会话，再次明确选择 Aimship。
3. 粘贴 Agent 给出的续接入口，其中使用回执里的实际交付目录：

> 使用 Aimship 继续交付「实际交付目录」，先读取当前状态和相关正式文档再接续。

Agent 会读取同一交付的已保存状态、相关正式文档和成果，说明当前停点与下一步。已有可信绑定时可直接定位；找不到或有多个候选时才询问目录。待审文档仍需审核，换会话本身不产生批准。

同一交付保持一个写入会话，资料与代码访问仍需可用。Aimship 提供续接入口，由你创建新会话；通常无需复制完整聊天。若在首次保存前必须换会话，携带 Agent 整理的未保存诉求、计划位置和待完成操作。

<a id="工作意外停止后继续"></a>
### 2.2 工作意外停止后继续

提供原交付目录，说明停止时的操作及已有错误信息。Agent 先核对实际文件、已保存进度和未完成操作，再继续工作。初始化中断或保存后进度页生成失败时，保留已有身份与资料，修复缺失部分。

代码仓库搬迁后提供新位置，由 Agent 核对身份后更新关联。状态冲突需先协调，进度页手改内容会先保留再核对和重建。

<a id="会话划分建议"></a>
### 2.3 会话划分建议

Agent 按适用工作给出建议分组，并显示在 `status.md`；可按任务规模、资料量和上下文情况调整。

| 工作内容 | 会话安排 |
| --- | --- |
| 需求／Scope | 一个会话 |
| 技术文档、SQL、接口文档 | 共用一个会话 |
| 测试用例设计 | 一个会话 |
| 实施计划 | 一个会话 |
| 实施 | 每个实施批次一个会话，包含该批 Agent 评审 |
| 整体 review | 一个会话 |
| 测试执行 | 每个测试批次一个会话 |

分组用于安排上下文，不是额外审批或阶段完成条件。共用会话仍按顺序逐份审核；实施批次与测试批次不必一一对应，也不要求逐批立即测试。新会话仍需读取完整相关材料，不能只依赖聊天摘要。

<a id="查看当前工作"></a>
### 2.4 查看当前工作

打开回执中的 **`status.md`**，查看当前阶段、待审文档、阻塞事项、下一步和成果入口。也可以直接询问：

> 当前交付进行到哪里，还有哪些内容需要我确认？

查看验证结论时，关注对应版本、环境与证据；缺少条件的检查标为阻塞或未执行。文件用途见[交付目录与文档](#delivery-structure)。`status.md` 由 Agent 维护，需求调整或验收意见直接在会话中说明。

<a id="验收交付成果"></a>
### 2.5 验收交付成果

阅读 `handoff.md` 中的成果位置、使用方式、审核与验证结论、遗留问题，对照原目标判断是否接受。可以明确回复：

> 我已检查本次订单导出成果，符合约定目标，验收通过。

存在差异时，说明具体行为与预期，Agent 会处理问题并更新交付结果。文档批准与最终验收分别记录；目标完成、用户验收、合并和部署也分别记录。

标准完整交付需要主线工作、必要批准、通过的批内／整体 review、独立验证和最终验收都有依据。明确缩减范围或未测试的成果会标明限制；旧交付保留原记录，按当前标准的评估情况单独说明。要求预览不改变交付目标；明确提前结束时保留未完成工作。

后续小修正可以继续原交付并保留此前完成记录；新目标或大幅重新设计建立关联的新交付。

## 3. 其他起点与工作安排

以下情况沿用首次使用和审核流程，只需补充相应材料或安排。

<a id="已有-prd原型或其他资料"></a>
### 3.1 已有 PRD、原型或其他资料

提供资料位置、采用版本和本次范围，并指出已知缺口。

> 使用 Aimship 根据这份 PRD 和原型完成订单导出，本次只采用“导出订单”部分。

Agent 核对资料的可访问性与覆盖范围，保留权威资料原件，通过 `scope.md` 记录采用内容、缺口和决定；零散参考用于编写需求。已有交互覆盖的部分直接复用，未覆盖的变化再补充。

采用外部资料时保留对应版本。若需直接维护已有可编辑 PRD，应明确委托，并确认它完整表达本次范围、授权和终点。

<a id="修改现有功能修复缺陷或重构"></a>
### 3.2 修改现有功能、修复缺陷或重构

提供仓库和功能位置，说明期望行为及必须保留的行为。缺陷附复现条件或日志；重构说明技术目标。

> 使用 Aimship 修复订单导出遗漏已选记录的问题。仓库位于「本地工程目录」，复现步骤如下……

Agent 可在需求阶段读取相关代码，核对现有行为和技术约束，再安排设计、实施、审核与验证。实施进度、审核和实际验证结果分别记录在 `plan.md`、`review.md` 和 `testing.md`。

<a id="将当前讨论转为交付"></a>
### 3.3 将当前讨论转为交付

在已有具体诉求的讨论中，明确要求使用 Aimship 承接当前内容。

> 使用 Aimship 处理刚才讨论的订单导出需求，保留已确认的字段和待决问题。

Agent 沿用当前可见的相关输入，保留原话、已确认决定和待决事项；不可见的历史会标明缺口。若尚未保存就需换会话，带上未保存上下文和计划资料位置，在新会话再次启用 Aimship。

<a id="需求开始后再关联代码"></a>
### 3.4 需求开始后再关联代码

代码准备好后，在原交付中提供可访问的本地工程位置。

> 将「本地工程目录」关联到当前订单导出交付，核对现有实现对需求的影响。

Agent 将代码关联到同一次交付并读取必要工程事实，资料目录保持不变。关联本身不修改代码；影响已确认内容的新事实按[需求变化](#changes)处理，实施仍遵循原有审核与授权。

<a id="同时推进多个需求"></a>
### 3.5 同时推进多个需求

不同需求使用独立交付目录，每个交付只保留一个写入会话。向 Agent 说明已知的共享代码、接口、数据库或测试环境。

一个需求正在修改代码时，另一个可以先做只读分析。两个需求都要修改同一份代码之前，安排串行实施或独立 checkout／worktree，并优先复用已有隔离。Agent 会根据可访问的已知交付记录核对重叠范围，在计划中记录协调方式；未知或过期记录、Aimship 外的工作不在完整掌握范围内。

各需求分别查看自己的进度和结果。分支完成不代表集成完成；Aimship 不提供全局锁、自动 Agent 调度、自动创建 worktree 或自动合并。

## 4. 常见问题与参考

### 4.1 常见问题

| 情况 | 如何处理 |
| --- | --- |
| 无法访问资料或代码 | 在当前 AI 工具授权需要的目录，说明失败的具体操作，不通过搬动资料绕过权限限制 |
| 进度页与实际成果不一致 | 请 Agent 核对当前记录和实际文件，保留手改内容后重建进度页 |
| 正式文档在会话外被修改 | 指出修改位置，请 Agent 核对含义及对后续工作的影响 |
| 旧交付无法继续 | 请 Agent 检查格式迁移、规则采用和文档整理，保留历史结果并说明阻塞原因 |
| 找不到 Aimship、安装或版本异常 | 查看 README 的[安装与升级问题](../README.zh-CN.md#installation-troubleshooting) |

反馈问题时提供 AI 工具和 Aimship 版本、具体操作、预期与实际结果，以及可复现的最小资料；隐去凭据、个人路径和业务数据，通过 [GitHub Issues](https://github.com/clsx/aimship/issues)提交。

<a id="升级-aimship-后继续已有交付"></a>
### 4.2 升级 Aimship 后继续已有交付

升级 Aimship 后，旧会话可能保留旧规则。先保存工作，再让 Agent 在稳定边界核对当前版本与交付记录；无法可靠刷新时开启新会话。旧格式交付需要明确迁移、采用规则并整理相关文档后继续，未知格式保持只读。已有原件和历史结果保留，不补造过去未执行的工作，也不将旧完成记录当作批准；恢复协议供 Agent 查阅 [CLI 文档](cli.md)。

<a id="ai-工具集成说明"></a>
### 4.3 AI 工具集成说明

AI 工具集成仍处于实验阶段，真实 Skill 发现、目录访问和跨工具接续仍待验证。安装文件健康不等于 AI 工具已加载 Skill。Codex 和 Cursor 共用入口，兼容 AI 工具也可能发现其他位置的入口；出现重复项时检查路径和版本，保留无关或定制内容。AI 工具行为可参考官方 [Cursor 文档](https://cursor.com/docs/skills)和 [Codex Skill 位置说明](https://learn.chatgpt.com/docs/build-skills)。

### 4.4 交付目录与文档

默认每个需求在 `~/Aimship/` 下使用独立交付目录，代码保留在原仓库。

下方列出交付产物及其用途；实际生成范围由约定交付范围和产物条件确定，无关工作不生成空文档。`prd.md` 与 `scope.md` 是需求入口的两种选择，并非每个需求都要同时生成。

```text
~/Aimship/
├── 20261023-订单导出/             # 每个需求一个独立交付目录
│   ├── status.md                 # 自动生成的进度总览和阅读入口
│   ├── prd.md                    # 自编需求：目标、范围、需求和验收标准
│   ├── scope.md                  # 采用权威外部资料时使用，替代自编 PRD
│   ├── tech-design.md            # 技术方案：架构、改动、数据、风险和需求覆盖
│   ├── plan.md                   # 实施计划：批次、任务及实际执行记录
│   ├── testing.md                # 测试用例、覆盖关系、执行与重测结果
│   ├── review.md                 # 各批及整体审核、发现的问题和处理结论
│   ├── handoff.md                # 交付结果、使用方式、验证结论和遗留事项
│   ├── diagnosis.md              # 仅独立调查时生成的定位与证据记录
│   ├── change-log.md             # 重要变更、决定及受影响的工作
│   ├── openapi.yaml              # 新建 HTTP 契约；已有权威契约优先复用
│   ├── database.sql              # 单数据库 SQL；多目标为 database-<id>.sql
│   ├── prototype/                # 符合生成条件时新建的原型
│   │   └── index.html            # HTML 原型入口，相关资源也放在此目录
│   ├── source/                   # 保留原始需求和采用的外部资料版本
│   │   ├── request.md            # 原始委托或来源入口
│   │   └── …                     # 外部 PRD、原型、截图及其他输入
│   └── .aimship/                 # 工具维护的内部状态与辅助证据
│       ├── state.json            # 阶段、引用、版本及仓库／worktree 关联
│       ├── state.previous.json   # 写入后用于恢复的上一版状态
│       ├── view.json             # 进度视图的生成元信息
│       └── evidence/             # 按需保留的验证等证据
└── 20261024-另一个需求/           # 独立的资料与进度
```

正式文档直接放在需求目录下；`source/` 保留采用的原件，`.aimship/` 保存内部记录。软件安装目录为 `~/.aimship/`，与各需求目录内的 `.aimship/` 分别管理。

<a id="固定大纲和可追溯编号"></a>
需求、验收标准、实施任务、审核和测试结果之间的关联由 Agent 维护，便于追溯。
