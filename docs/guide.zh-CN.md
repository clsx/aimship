## 1. 在 AI 工具中选择 Aimship

安装后开启新的 AI 工具会话，选择 Aimship：

| AI 工具 | 如何选择 | 未显示时 |
| --- | --- | --- |
| Codex | 在 Skill 选择器中选择 Aimship；CLI 中使用 `$aimship` | 新建会话或重启 CLI，列表未刷新时重启应用 |
| Cursor | 使用 `/aimship` | 新建 Agent 会话，检查 Customize → Skills；列表未刷新时重启 Cursor |
| Claude Code | 使用 `/aimship` | 新建会话并检查斜杠命令列表；列表未刷新时重启 Claude Code |

每个 AI 工具分别需要登录、可用模型以及交付资料和相关代码仓库的访问权限，在实际操作需要时授权。交付资料单独保存，代码仍在原仓库中。

AI 工具集成仍处于实验阶段，真实 Skill 发现、目录访问和跨工具接续仍待验证。安装文件健康不等于 AI 工具已加载 Skill。Codex 和 Cursor 共用入口，兼容 AI 工具也可能发现其他位置的入口；出现重复项时检查路径和版本，保留无关或定制内容。AI 工具行为可参考官方 [Cursor 文档](https://cursor.com/docs/skills)和 [Codex Skill 位置说明](https://learn.chatgpt.com/docs/build-skills)。

## 2. 不同场景下如何开始

### 尚未形成需求文档

说明想解决的问题、使用者、期望变化和已知限制。有截图、讨论记录或参考资料时一起提供，无需先准备完整 PRD。

Agent 会澄清目标、范围和验收判断中的缺口，整理需求与验收标准，并说明后续工作安排。你确认目标和重要取舍后，Agent 继续推进。需求与验收标准通常记录在 `prd.md`，当前进度从 `status.md` 查看。

### 已有 PRD、原型或其他资料

提供资料位置、准备采用的版本，以及相关代码位置；如果只采用部分内容，说明本次范围。已有资料不完整时，可以直接说明已知缺口。

Agent 会核对资料是否可访问、是否覆盖本次目标。采用权威 PRD／原型时，保留原件，通过 `scope.md` 记录采用范围、缺口和决定；零散参考则用于编写需求。已有交互被充分覆盖时复用，未覆盖的变化再补充。你可从需求文档和关联资料中查看采用了哪些内容、还需决定什么。

### 修改现有功能、修复缺陷或重构

提供相关仓库和功能位置，说明期望行为、当前问题及必须保留的行为。修复缺陷时附上可用的复现条件、错误信息或日志；重构时说明技术目标和不能改变的外部行为。

Agent 会检查相关实现，确认需求与技术约束，安排设计、实施、审核和验证。普通调试随当前工作处理；重大未知问题需要独立调查时，再调整安排。`plan.md` 记录实施进度，`review.md` 和 `testing.md` 分别记录审核与实际验证结果。

外部材料按采用版本保留原件，链接本身未必保留版本，访问缺口应明确。只有你明确委托维护现有可编辑 PRD，且它完整表达本次范围、授权和终点时，才登记复用；不能仅凭“以前由我们编写”就修改采用的原件。

以上场景都由 Agent 保留原始委托并维护交付记录。重要的业务、范围、兼容性、成本或数据决策由你决定；授权内的日常技术取舍由 Agent 处理。待决问题没有回应时不会被视为批准，相关依赖工作等待解决。

## 3. 推进与审核

标准主线是需求和验收标准 → 技术设计及适用的接口／SQL／交互产物 → 测试用例 → 实施计划 → 分批实施（含批内 review）→ 整体 review → 测试验证 → 交付验收。Agent 根据需求落实这条主线，不要求你逐项勾选核心阶段；无关产物不生成，已有正式材料先核对采用，采用不等于批准。

每份需人审文档生成、自检后，Agent 展示当前阶段状态、文档入口和审核重点，等待你明确通过或提出问题。讨论、沉默和要求看结果都不算批准；修改后自检并重新送审。待审期间不提前提供下一阶段的续接提示。

你明确通过后，Agent 在一次处理中记录批准及文档版本、保存进度和下一步、检查保存结果，再给出下一步建议。无需分别确认保存或提示词；保存失败时会如实说明。同一建议会话组内直接衔接下一项，不再询问是否开始；到组间边界则建议新会话并给出简短入口，本轮不同时执行下一阶段。你说“在当前会话继续”即可直接继续，不增加审批，具体见[会话划分建议](#continue)。

如果你明确不要测试用例和测试，Agent 会一次说明并记录范围，完成授权的开发与 review 后交接**未测试的阶段性成果**，不会偷偷补做或反复劝说。阶段性范围完成不等于标准完整交付完成，也不能写成验证通过。文档批准与最终交付验收分别记录。

授权内的实施、批内检查／修复和复测可继续推进；review 或测试发现问题时先修复或按既有规则回流。新增实质决定和生产动作仍需对应授权。

## 4. 查看进度与成果

从交付目录的 **`status.md`** 查看当前阶段、待审文档、审核状态、阻塞事项、下一阶段和成果入口。查看验证结论时，同时关注对应版本、环境和证据。缺少账号、工具或环境的检查会标为阻塞或未执行，不能计为通过。

### 交付目录与文档

默认每个需求在 `~/Aimship/` 下使用独立交付目录，代码保留在原仓库。

下方列出交付产物及其用途；实际生成范围由约定交付范围和产物条件确定，无关工作不生成空文档。`prd.md` 与 `scope.md` 是需求入口的两种选择，并非每个需求都要同时生成。

```text
~/Aimship/
├── 20261023-订单导出/             # 每个需求一个独立交付目录
│   ├── status.md                 # 自动生成的进度总览和阅读入口
│   ├── prd.md                    # 自编需求：目标、范围、需求和验收标准
│   ├── scope.md                  # 采用权威外部资料时使用，替代自编 PRD
│   ├── tech-design.md            # 技术方案：架构、改动、数据、风险和需求覆盖
│   ├── plan.md                   # 实施计划：批次、任务及实际执行记录
│   ├── testing.md                # 测试用例、覆盖关系、执行与重测结果
│   ├── review.md                 # 各批及整体审核、发现的问题和处理结论
│   ├── handoff.md                # 交付结果、使用方式、验证结论和遗留事项
│   ├── diagnosis.md              # 仅独立调查时生成的定位与证据记录
│   ├── change-log.md             # 重要变更、决定及受影响的工作
│   ├── openapi.yaml              # 新建 HTTP 契约；已有权威契约优先复用
│   ├── database.sql              # 单数据库 SQL；多目标为 database-<id>.sql
│   ├── prototype/                # 符合生成条件时新建的原型
│   │   └── index.html            # HTML 原型入口，相关资源也放在此目录
│   ├── source/                   # 保留原始需求和采用的外部资料版本
│   │   ├── request.md            # 原始委托或来源入口
│   │   └── …                     # 外部 PRD、原型、截图及其他输入
│   └── .aimship/                 # 工具维护的内部状态与辅助证据
│       ├── state.json            # 阶段、引用、版本及仓库／worktree 关联
│       ├── state.previous.json   # 写入后用于恢复的上一版状态
│       ├── view.json             # 进度视图的生成元信息
│       └── evidence/             # 按需保留的验证等证据
└── 20261024-另一个需求/           # 独立的资料与进度
```

正式文档直接放在需求目录下；`source/` 保留采用的原件，`.aimship/` 保存内部记录。软件安装目录为 `~/.aimship/`，与各需求目录内的 `.aimship/` 分别管理。

<a id="固定大纲和可追溯编号"></a>
需求、验收标准、实施任务、审核和测试结果之间的关联由 Agent 维护，便于追溯。

## 5. 推进中需求发生变化

说明发生了什么变化、原因以及希望保留的内容。如果已修改正式文档，指出位置，让 Agent 核对修改的含义。

Agent 会分析对范围、设计、实现和验证的影响，记录决定，更新受影响的工作安排和文档。需要你判断的取舍会提出，其他授权内工作继续，原始采用资料继续保留。

已批准文档发生实质变更时，回到对应阶段重审，依赖它的工作等待审核解决后再继续；旧批准和结果保留为历史，不能用旧批准放行新版。重审通过后，按依赖顺序恢复。无关工作不重置，排版和错字修正不需全量重审。

重要变化及影响记录在 `change-log.md`，后续安排从 `status.md` 查看。不要通过修改 `status.md` 来改变需求或表示验收；它是生成视图，已有手改内容需先保留，再由 Agent 核对和重建。

## 6. 会话安排与继续工作

### 会话划分建议

以下安排基于实际项目中的使用经验，可按任务规模调整。交付初建或需求确认时，Agent 会将适用的建议分组记录在状态中，并显示在 `status.md`：

| 工作内容 | 会话安排 |
| --- | --- |
| 需求／Scope | 一个会话 |
| 技术文档、SQL、接口文档 | 共用一个会话 |
| 测试用例设计 | 一个会话 |
| 实施计划 | 一个会话 |
| 实施 | 每个实施批次一个会话，包含该批 Agent 评审 |
| 整体 review | 一个会话 |
| 测试执行 | 每个测试批次一个会话 |

这是使用经验，不是强制会话划分规则或阶段完成条件。可按任务规模、资料量和上下文累积情况调整；合并后的效果需在实际工作中核对。技术文档、SQL 和接口共用会话时，仍按既定顺序先审技术文档，再逐份审核适用的接口／SQL 文档，不能因为共用会话而跳过审核。

实施批次与测试批次承担不同工作。测试批次按验证安排划分，不要求与实施批次一一对应，也不要求每个实施批次结束后立即测试。新会话本身不保证判断独立或质量；每个新会话仍需读取相关的完整正式文档、已保存状态和实际成果，不能只靠简短聊天摘要接手。

### 安排新会话与交接

到建议会话边界，Agent 先确认批准、成果和状态已保存，再说明当前成果与下一步，建议新会话并提供一行可复制入口，其中使用真实交付目录：

> 使用 Aimship 继续交付「实际目录」，先读取当前状态和相关正式文档再接续。

你无需每次批准时再强调要换会话，也无需分别确认保存或生成提示词。可以直接回复“在当前会话继续”；会话划分只是上下文建议，不是审批或阻塞条件。最后交付结束时不提供无意义的下一阶段入口。需要完整提示词时可以提出，默认不逐阶段输出长提示词，也不新建提示词或交接文件。

Aimship 本身不创建新会话。等当前会话确认保存并停止写入后，在 AI 工具中开启新会话，选择 Aimship 并粘贴入口。新会话必须唯一定位同一交付，核对实际状态、文档审批版本、相关完整正式文档、实际成果和未完成操作，再确定行动。已有可信绑定时不重复索要路径；没有明确绑定或有多个候选时会询问目录，不能猜“最近一个”。单说“继续下一阶段”或复制旧提示词不会形成新的批准，待审草案换会话仍然待审。

同一交付只保留一个写入会话。代码位置和访问权限仍需可用，不能因换会话绕过审核或受影响工作的停点。进度始终从同一份 `status.md` 查看，无需复制完整聊天。

### 工作意外停止后继续

如果 Agent 因断网、工具退出或操作取消而停止工作，告诉它停止时正在处理什么，并提供已有错误信息。继续前，Agent 会核对实际文件、已保存进度及未完成操作，确认哪些操作已经完成，避免重复写入或重跑有副作用的动作。

代码仓库搬迁后提供新位置，由 Agent 核对身份后更新关联。状态冲突或进度视图异常需要先协调或修复，不能强行覆盖。

### 升级 Aimship 后继续已有交付

升级 Aimship 后，旧会话可能保留旧规则。先保存工作，再让 Agent 在稳定边界核对当前版本与交付记录；无法可靠刷新时开启新会话。旧格式交付需要明确迁移、采用规则并整理相关文档后继续，未知格式保持只读。已有原件和历史结果保留，不补造过去未执行的工作，也不将旧完成记录当作批准；恢复协议供 Agent 查阅 [CLI 文档](cli.md)。

## 7. 同时推进多个需求

不同需求使用独立交付目录，每个交付只保留一个写入会话。向 Agent 说明已知的共享代码、接口、数据库或测试环境。

一个需求正在修改代码时，另一个可以先做只读分析。两个需求都要修改同一份代码之前，安排串行实施或独立 checkout／worktree，并优先复用已有隔离。Agent 会根据可访问的已知交付记录核对重叠范围，在计划中记录协调方式；未知或过期记录、Aimship 外的工作不在完整掌握范围内。

各需求分别查看自己的进度和结果。分支完成不代表集成完成；Aimship 不提供全局锁、自动 Agent 调度、自动创建 worktree 或自动合并。

## 8. 完成交付

查看交接记录中的成果位置、使用方式、审核和验证结论、遗留问题与后续事项，并对照原目标判断是否接受。

Agent 会分别记录目标完成、用户验收、合并和部署的实际情况。要求预览不代表缩短目标；明确提前结束时，交接中保留原目标和未完成工作。

标准完整交付需要主线工作、必要文档批准、通过的批内／整体 review、独立验证及最终验收都有依据。`status.md` 将标准完整性与约定范围的完成、用户验收分别显示；工具核对记录，不能独立证明测试真实执行或内容正确。明确缩减范围的成果可完成并交接，但会显示为阶段性范围；未测试就明确写未测试。旧交付保留原完成和验收记录，先标为尚未按新标准评估，核对证据并明确采用新规则后再续接，不补造历史审批或测试。

后续小修正可以继续原交付，并保留此前完成记录；新目标或大幅重新设计则建立关联的新交付。

<a id="troubleshoot"></a>
<a id="8-使用中遇到问题"></a>
## 9. 使用中遇到问题

| 情况 | 如何处理 |
| --- | --- |
| 无法访问资料或代码 | 在当前 AI 工具授权需要的目录，说明失败的具体操作，不通过搬动资料绕过权限限制 |
| 进度页与实际成果不一致 | 请 Agent 核对当前记录和实际文件，保留手改内容后重建进度页 |
| 正式文档在会话外被修改 | 指出修改位置，请 Agent 核对含义及对后续工作的影响 |
| 旧交付无法继续 | 请 Agent 检查格式迁移、规则采用和文档整理，保留历史结果并说明阻塞原因 |
| 找不到 Aimship、安装或版本异常 | 查看 README 的[安装与升级问题](../README.zh-CN.md#installation-troubleshooting) |

反馈问题时提供 AI 工具和 Aimship 版本、具体操作、预期与实际结果，以及可复现的最小资料；隐去凭据、个人路径和业务数据，通过 [GitHub Issues](https://github.com/clsx/aimship/issues)提交。
