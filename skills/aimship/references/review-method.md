# Shared review method

Fix the reviewed object first: requirements/design/plan basis, repositories, commit plus relevant differences/untracked files, or document sections/digests. Use the [shared project context](core.md#project-context-and-decisions) and inspect only the commissioned scope and its dependencies. Review actual correctness against requirements/design/contracts, relevant conventions, logic, state, transaction/consistency and failure paths as applicable. Neither copying the design nor compiling proves correctness; review is separate from executing the testing plan.

Record a REV in review.md with scope/object, assessment and findings. A finding gives impact/severity, file/section/symbol, concrete problem, disposition and repair/recheck reference. If there are no findings, say so briefly; do not emit an empty issue table or implementation/test-command transcript. Reference existing evidence where it supports the conclusion.

Keep historical REV conclusions for their original objects. A passing recheck names the repaired object and explicitly references the conclusion it replaces; a failed or unexecuted check stays failed or unknown. Submit the review facts and coverage through the state tool; its generated current section identifies the effective result and outstanding review references. Keep the finding explanations, repair dispositions and historical REV conclusions in AI-maintained sections, rather than hand-maintaining a second current-result table or competing old instructions. Existing document-content approvals remain separate from code-review records.
