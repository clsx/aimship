# Shared delivery core

## User-facing updates

Apply the workflow internally. Explain the actual result, retained/adopted inputs, useful artifact links, current stop and next action in the delivery language. A review request names the AI-produced document and its concrete review focus; a clarification gives the choice, recommendation and impact; a completed stage says what was saved and what continuation will do. For example: “技术设计已保存，请查看接口边界与错误处理，确认通过或提出修改。” Give this practical reason for the stop rather than quoting internal Skill instructions or linking their rules. Explain rules when the user asks or troubleshooting needs them.

This is presentation guidance, not permission to skip rules or hide facts. Keep useful PRD/business-source and artifact links, actual access limits, errors, unsaved work, required approvals and material risks visible. Translate a tool diagnostic into its concrete effect and next step without claiming success; include a relevant error/code when useful. Technical CLI JSON, rule paths and diagnostic notes remain available to the Agent and for troubleshooting, not a script to paste into every reply. When the user asks why, asks to inspect product rules or needs technical diagnosis, explain the relevant basis and link it as needed. Do not filter or rewrite saved user text to enforce this guidance.

## Start from the commission

A delivery has one centralized material directory, initialization notes containing the original commission, a state record, and a current PRD, authored or adopted as needed. The default endpoint is implementation, review, independent verification and delivery acceptance; retain any explicit limit in the commission. Code stays in its existing locations. A single repository and several repositories use the same model; there is no project registration step, repository count limit, or route classification.

The project workspace is the AI tool's working context, not necessarily a code repository. Initialization needs no code location or repository association. Work in that workspace and, using the tool's supported controls when needed, have the user add or grant access to the actual delivery directory in place; do not copy its documents into the workspace. Do not invent workspace membership when it is unknown or claim to add a folder automatically. The configured dataRoot remains the default, not a new Aimship folder relative to the working directory.

Understand the intended result, supplied evidence, authorized changes and endpoint. Record known answers instead of asking again. Clarify only gaps that affect this work, with a recommendation and its consequence. Do not promote assumptions into user decisions. A delivery may start without a repository; a design-only commission may never need one. A short bug fix still needs its original report, context, expected behavior, scope and acceptance criteria, with a concise prd.md using the fixed outline.

Use the dataRoot returned by bind (default `~/Aimship`), with a separate identifiable folder for each new delivery; the root itself is not a delivery. A project, code checkout or prototype directory describes existing materials, not a request to store the delivery there. Check possible existing matches before creating anything; ambiguous candidates need selection, not a global “latest” pointer. Only an explicit user choice changes the new delivery location. If access fails, retain the request and intended location in the conversation, report what is unsaved and resume there when access is restored; never fall back to the current workspace. Installation does not create delivery materials.

Read repository instructions and existing tools for the relevant work. Record relevant pre-existing modifications in existing engineering state, design or plan records and distinguish them from the delivery's changes. Do not paste full Git dirty lists into a business PRD. Other requests' changes are not this delivery's scope; a dirty tree alone is not a blocker. Do not clean a working tree, initialize Git, modify an unrelated repository, or expand write access merely to simplify the workflow.

## Initialize or resume the same delivery

This flow follows explicit Aimship activation in the first and every new session. Opening a project or merely mentioning Aimship does not activate it. A concrete problem, defect, technical objective or intended change is sufficient; a complete PRD, code and technical stack are not prerequisites. With only a product name or broad direction, ask a focused question about the actual problem before creating records; do not invent features or a full product scope.

1. Preserve the user's relevant wording, sources, constraints and visible discussion. Distinguish user decisions, reported facts, Agent suggestions and unknowns. Do not re-ask known answers or treat discussion as approval. Before write access exists, keep this in the conversation and say it is not saved. If a session switch is necessary before saving, provide copyable context with the intended path, original input and pending operation; it is not a new approval.
2. Bind the actual tool/core version and keep its returned dataRoot. Inspect the intended delivery folder or known candidates for existing state, partial creation or conflicting material. Read and resume existing state, checking deliveryId when known, including older deliveries outside today’s configured root. For a new location explicitly chosen by the user, preserve that actual decision in a nonempty local file within the delivery and supply `storage: {mode: "explicit", decisionRef: "<delivery-relative file>"}` to init; the reference is a file path without a fragment. Never invent the decision or override the tool’s dataRoot to make a path pass. Otherwise use a separate folder under the bound dataRoot. Ask only when identity/location is unresolved; do not create a replacement or infer ownership from a matching name.
3. Reuse the current workspace’s access to the intended materials path without changing that path. If access is missing, follow [AI tool access](hosts.md) with the exact required path; the user adds the original directory or grants the needed access. If the target does not exist, use its accessible existing parent to create it as part of saving this delivery, or explain which directory the user must create/open. No silent fallback into the workspace, unrelated probe files or global settings changes. Workspace names and “I added it” are not proof: normal reads establish read access only; actual saves establish write access for that operation. Do not report saved work before the result confirms it.
4. Write concise initialization notes in .aimship/init.md: the original commission in its own words, language, supplied material locations, adopted copies, explicit user limits and the delivery endpoint. Distinguish the user’s words from your summary. Keep stable context here, current progress in state/status and business changes in formal requirements; date any necessary initialization-time observation so it cannot be mistaken for current execution. Do not duplicate the general workflow or conversation history. Set `language` to `zh-CN` or `en`: an explicit user preference takes precedence, otherwise use the language of this conversation. The Agent saves this delivery setting in init; it is not an installation setting or a command the user must learn. Use init to create state and its generated status.md. An omitted or null endpoint defaults to standard delivery; provide an actual narrower endpoint when the user limits the work. Before PRD exists, use goalRef .aimship/init.md, empty documents and null for unknown documentPolicy conditions/authority (schema 5). A requirements/frame run can be active without a draft; a done result still requires its formal artifact. Do not create empty templates or mark unknown conditions false/none/[] to pass init. Use next for the concrete pending questions/work; no parallel initialization ledger.
5. Inspect stateSaved, revision and view from the actual result. Read back the saved state and status entry before reporting complete initialization. If the view failed, preserve the ID/revision and repair it with render; do not init again. If the response was lost, read before retrying. Source-only partial creation resumes at the same intended location after checking its ownership; stale locks require confirming the writer stopped.
6. Give a concise receipt: initialized / resumed / incomplete, recognizable delivery, actual absolute directory and readable status link (only when available), saved materials, bound version, saved language, code association and checked access, current stage/work and next action. A repository registration alone does not prove access. Do not claim original initialization facts for an old delivery. Separate existing materials retained or copied from documents newly authored or revised and delivery records newly created. Report “unchanged” only when supported by the actual operations and source evidence. For a complete unchanged supplied PRD with clear intent to deliver from it, report input adoption without requesting repeated source approval; clarify only actual uncertainties. On first initialization, add one neutral reminder with the actual directory: add it to the current project/workspace, ignoring this if already added. No tool-specific instructions or membership check are needed. Then continue authorized requirement clarification, unless the user requested a stop.

Register the first substantive PRD, select its authority and change goalRef in the same update when drafting it. This reference transition alone does not alter the user's goal or require a fabricated approval; an actual endpoint/scope change still needs its decision source. AI-authored or substantively revised requirements and subsequent selected reviewable outputs keep their self-check/explicit-approval stops. An unchanged supplied PRD/prototype uses mode input and its actual adoption-request basis; self-check makes it usable input, not human-approved AI output. Internal management records are not separately reviewed. Write new formal headings/body and next-action text in the saved delivery language while retaining business IDs, machine keys and paths. Preserve source text and existing documents without automatic translation. Unknown technical conditions can be investigated during design, but must be resolved before completing design or advancing work that depends on them. Omitting a stage record cannot bypass its input document approvals.

“Clarify requirements first” describes current work, not a requirements-only endpoint or full development permission. The standard stage sequence is the default, not a choice to ask again in the receipt or next action. Clarify only a concrete unresolved scope or endpoint condition that affects the work; do not ask whether to follow the standard sequence. Use the standard endpoint for normal delivery; record an explicit limitation when one is actually given. Keep known conditions when available; false/none/[] mean explicitly not applicable, not unknown. Later changes use existing impact/re-review rules.

### Associate code when needed

Code prepared by the user can be associated later through repositories in the same state, preserving deliveryId, sources and approvals. Read relevant engineering facts during requirements when they affect current behavior or feasibility; do not force waiting until implementation. If only a remote URL is supplied, record the source and request an accessible local checkout when needed; do not clone by default. Read repository instructions, actual checkout identity, version/commit and pre-existing changes; a non-Git directory or missing version is recorded honestly. Check known overlap below. Association itself does not authorize code writes, branch changes, dependency installs or publication. New facts trigger only the necessary impact assessment; unchanged decisions remain intact.

## Independent deliveries and recorded overlap

Several independent deliveries may progress at the same time, each with its own material directory, goal, stages and state. One writing session **per delivery** is not a product-wide single-task limit. This check is workspace preparation based on records, not a cross-session lock or scheduler.

Check when code scope is associated or changed, before entering implementation, or when an actual code working directory changes. Do not repeat it every turn or stage. Once the code scope is known:

1. Enumerate all delivery directories in the accessible configured material root and any other explicitly known/authorized material roots or delivery locations. Use `scan <known-root>` to read `.aimship/state.json` summaries; deduplicate deliveryId and report conflicting copies; do not limit the search to recent folders. Do not scan the whole disk, code trees, processes, PRDs or full histories. Do not discover unknown custom roots by searching the home directory. Report roots checked and inaccessible, invalid or unknown-format records; unseen custom roots and non-Aimship work remain outside the check.
2. Exclude this delivery by `deliveryId`. Compare `repositories[].path` (the actual checkout/worktree root), role, `currentRun`, relevant `stageRuns` scope/progress, `outcome`, `next` and recorded update time. Repository IDs are local to each delivery and are not global repository identity. Use already recorded repository identity; when needed and accessible, read only local Git root/common-directory metadata for the associated paths to distinguish linked worktrees. Normalize existing paths to their actual location; nested paths in one checkout are not independent isolation. Distinct independent checkouts may share a recorded repository identity even with different Git directories. If identity/location cannot be established, report it as unknown rather than assuming separation.
3. Include older active, blocked or uncertain deliveries. A `done` stage, completed handoff, old timestamp or declined acceptance alone does not close a delivery. A recorded met goal with no recorded remaining code work is ended; otherwise use the existing explicit closing conclusion if needed. `not-met` or `unknown` is not automatically ended. Read only the relevant engineering plan/conclusion section when state summaries cannot establish writing intent or closure. Do not rewrite another delivery's state. Ended deliveries are not active writers, although their unmerged results or known dependencies can still matter.
4. Compare actual writing intent and locations using the table below. A stage label alone is not permission to write code. Keep one brief result in the existing engineering plan or results section, linked from the current delivery's existing references when needed: check occasion, roots/limits, relevant delivery IDs and recorded stages, actual directories, known dependencies and chosen arrangement. State stays authoritative; do not add a registry, index, second progress ledger or service.

| Recorded situation | Action |
| --- | --- |
| No known overlap | Continue without a new confirmation. Say “no overlap found among the recorded deliveries checked,” never guarantee there is no conflict. |
| Same repository, current work is requirements/design or explicitly read-only | Briefly identify related delivery and scope; continue that non-writing work and record any known business/interface dependency. Recheck before implementation. |
| Multiple deliveries preparing to modify the same actual checkout | Do not silently write concurrently. Identify the deliveries and recorded stages; use the user's existing choice of sequential implementation or a separate worktree/checkout. If unresolved, propose those choices and hold only the affected code writes. A recorded blocked writer does not prove its workspace has been released. |
| Same repository, distinct existing worktrees/checkouts | Reuse the existing isolation, do not create it again. File isolation does not guarantee conflict-free merging or compatible business changes. Record integration dependencies where known. |
| Different repositories with known shared API/database/test data/service | Record dependency and necessary sequencing or use arrangement in the existing plan. Do not operate real shared environments without authorization or build automatic dependency analysis. |

Records can be stale and cannot detect all other work. Do not switch another session's branch, stash, overwrite or clean unknown changes. The state tool's short write lock/revision check protects an individual state update; it does not reserve a checkout or enforce this workflow across sessions.

## Agree an ordered arrangement

Use the standard delivery sequence for a developer responsible for a requirement: requirements and acceptance criteria → technical design with applicable interface/SQL/interaction artifacts → test cases → plan → implementation batches with batch review → overall review → verification → handoff and acceptance. Do not offer an arbitrary checklist of core stages or a pluggable workflow. Internal runs and batches organize this sequence. Requirements and scope alignment are always needed; use the fixed PRD conditions in [document patterns](document-patterns.md). Adopt adequate existing artifacts as inputs without claiming their stages were newly executed. Do not create empty stage runs or templates.

Start requirements intake using this standard sequence. Do not offer a default full-delivery/design-only/initialization-only choice. Record the standard endpoint without a separate scope-selection question; explicit limitations or pauses take precedence. Keep actual document review decisions separate from this initial arrangement. Once confirmed, follow the order; material changes follow [change flow](sources-and-changes.md). A stage may recur as distinct instances with stable IDs and explicit scopes.

Explain each design's key decisions, why they fit the requirements, tradeoffs, artifact location and remaining questions. Ordinary implementation choices and necessary engineering dependencies stay with the agent within the commission; adding a repository alone is not a business-scope change. Explain material effects on goals, external behavior, compatibility, cost, data handling or explicit technical commitments and obtain the relevant decision. Keep distinct choices separate, with their own impact, recommendation and dependent work; only an unresolved dependency holds that work. Follow [document review](document-review.md): present each selected reviewable document after self-check and pause for explicit approval. An approval releases the next authorized work; use the session boundary interaction below, without a second approval or start confirmation.

Standard development order: PRD → technical design → interface/SQL → test cases → plan → implementation/review/verification → handoff. Generate only applicable artifacts. Inspect existing formal materials and register adoption without treating adoption as approval. Respect an explicitly limited commission without presenting it as standard complete delivery.

### Standard completeness and limited scope

New deliveries use `deliveryPolicy: {version: 1}`. `outcome.goal` describes the agreed scope and `outcome.acceptance` the actual user decision; neither alone means standard complete delivery. The tool reports a separate derived completion assessment. Standard completion requires reviewed requirements/design/cases/plan and applicable artifacts, completed implementation with passing batch and overall review, passing independent verification, handoff and explicit final acceptance. Register approved business batches separately from execution runs. Record review coverage with reviewOf implementation IDs and explicit reviewScope: batch or overall; repairs keep the business batch identity when applicable. Records validate structure/evidence references, not truth or user identity; inspect actual results and coverage.

If the user explicitly excludes cases and testing (or limits the commission to an earlier endpoint), explain the consequence once, preserve that scope decision in existing PRD/change records, and register `deliveryPolicy.partialRef`. Do not quietly add the excluded work or repeatedly persuade the user. Finish the authorized work and hand off the untested or otherwise limited result, recording omitted work and remaining limits. Its agreed scope can be met and accepted, but its completion assessment stays partial-scope, never standard-complete or verified. No special external-testing mode or extra documents are needed. Existing implementation/approval dependencies still apply. Scope changes preserve the earlier goal/decision/history; started runs are not erased to manufacture completion.

Current completion claims require the recorded scope, approvals and actual results. Saved business history does not replace current evidence.

### Begin or resume the selected work

Use the current state, relevant formal documents and selected stage contract to establish the work being continued or started. Each run records scope, inputs, results and progress; `done` is completed production, not human approval. At a new stage or batch, check its actual prerequisites, current-content approvals or adopted-input checks and the existing authorization. Use its ordinary run-start save (`record-run` with progress `active`) before substantive execution, especially before implementation code changes, and inspect the save result. Resolve an actual prerequisite or save problem within its affected scope; do not perform the work first and register its start afterward.

Reuse an already active run for the same work. Read-only preparation, discussion and document revisions within the current stage do not require a new run or another start check on every action. If the work or its inputs change materially, use the existing change/review rules. Do not ask again for approval or continuation already given.

Read/check/resume describe the recorded work: current-run `canProceed` is not permission to start the next stage, and successful `check` is not document approval. While design awaits review, discussion of implementation details and requests to refine the design stay in design; they do not by themselves authorize code implementation. An issue holds only dependent work; an actual change to the arrangement follows the existing plan/decision flow.

## Project context and decisions

Use the relevant current implementation, interfaces, database structures and applicable repository conventions to understand this change. Investigation, design, contract/SQL, implementation and review reuse that context according to their responsibilities. Existing code is evidence, not a requirement to copy it or repair unrelated historical debt. Read the applicable parts of available instructions; when none exist, use the current code/contracts and user requirements and proceed. Do not require a new conventions/context document or whole-project compliance proof.

Investigate facts accessible through the code, documents and tools instead of turning that work into questions for the user. Present only substantive business, authorization or design decisions with their impact, recommendation and dependent work. Hold the work that needs that answer; nonblocking details can remain for later investigation or verification. A design review need not resolve every future execution condition, but must disclose gaps that affect the decision or correctness of the next work.

## Implementation and evidence

Complete one authorized implementation work unit (implement → necessary development checks → automatic batch review → authorized repair/recheck), save and report its closure, then stop before the next batch. Compile/type checks and local tests are development self-checks, not code review or formal verification; choose them for the actual change rather than requiring a full suite after every batch. Planned tests can be written with implementation; writing them does not mean they passed. Keep brief development checks and existing evidence references in plan execution.

After the last batch and its review are complete, summarize implementation and remaining work, save and stop. Recommend a new session for the existing overall-review responsibility; do not start it automatically. Explicit authorization to continue overall review in the current session permits that path, without a special phrase, session proof or extra approval record. This also applies to a single business batch: its batch review does not replace overall review. Overall review examines the combined current object and stops before formal verification. A review request alone does not commission execution of the test plan.

After passing overall review, hand over the reviewed object, agreed environment preparation and formal verification scope. Use the actual project conditions: where testing requires a deployed test environment, it must be ready for that execution; local units or other agreed checks need no deployment. Aimship does not initiate deployment or add a deployment stage. Formal RUN records and optional coverage-based groups belong to testing execution. Groups follow coverage and conditions, not development batches; retests are new RUNs, not new business batches.

For standard delivery, registering review/verify/handoff as active or done requires their actual predecessors even when dependsOn or inputRefs are empty: review identifies completed implementation objects (an overall review covers all preceding batches), verification follows a passing overall review and resolved preceding reviews, and handoff follows passing verification or an evidenced passing rerun. Draft documents and planned work may be saved earlier. Independent review, verification or limited handoff requires the existing deliveryPolicy.partialRef to point to readable local evidence of the explicitly limited commission; an empty dependency list is not such authorization. Existing declared dependencies and document approvals still apply. These are state-tool checks, not interception of general-purpose file, test or deployment tools.

Record review and verification against actual objects: repository ID, commit if any, relevant uncommitted/untracked paths and content digests or necessary patch, scope and baseline. Distinguish pre-existing changes. A branch name alone is insufficient. For documents record file/section and the content basis; preserve necessary old excerpts when a digest would not explain the reviewed meaning.

Each conclusion identifies who/what produced it, date, object/version, scope, basis, result and evidence. Distinguish user review, agent review, actual execution and user-reported results. Actual verification also records commands or operations, environment/data, case document version and unexecuted checks. If the object changes during testing, determine which results remain applicable and retest affected checks.

Execution progress (`planned`, `active`, `blocked`, `done`) is separate from pass/fail/not-run/unknown, current applicability, goal achievement and user acceptance. A finished failed verification is still failed. Review is not runtime testing. Neither the presence of a report nor successful tool exit proves the goal.

### Conditional host delegation

Use the host's existing subagent capability when there are independent work blocks and the benefit exceeds coordination cost. Small work, shared-write conflicts or hosts without that capability proceed serially. Do not split frontend/backend automatically. Give each delegated block the relevant approved design/contracts, project context, scope and nonoverlapping write boundary. The main agent gathers required results, checks integration and completes the batch review, then records the delivery facts through the same state tool. Actual delegation is evidenced by host tool activity, not role-played summaries. Delegation adds no delivery stage, business batch, scheduling store, host plugin or proof gate, and does not make results inherently correct.

## State and stopping

Use the installed tool's documented state protocol. Read the current revision before a write and provide the expected revision; never bypass a conflict by blindly increasing it. State stores summaries and references, not copies of requirements or test reports. Persist the unfinished intent before changing multiple documents, then verify the artifacts before recording completion. No cross-file transaction is promised.

Important semantic changes retain historical review and test facts, mark affected conclusions for review and update the current editable authority. Do not overwrite external adopted sources. See [sources and change flow](sources-and-changes.md).

At each user-visible work-unit boundary, save the completed work and self-check, show its artifacts, actual stop and next action, then stop. Implementation and batch review save separate runs as internal checkpoints in one authorized batch work unit; continue its review/repair before the batch stop. A real permission, scope, approval or technical dependency can stop that work earlier. Existing sessionGroup is contextual grouping, not authorization. Overall review and formal verification remain distinct stops. Recommend a new session at the major boundaries below without requiring one; no session approval record or changed-session-ID proof.

Recommend switching after requirements are ready for technical design, after design and applicable contracts before test design, after the plan before implementation, after an implementation batch and its review, and after overall review before independent verification. Combine coinciding boundaries. Directory creation alone, individual documents inside a design group, test design before planning, and implementation before its batch review do not need another suggestion. For a pending document at a major boundary, recommend resuming its review, not starting the next stage. A failed review stays with its repairs.

For a reviewable draft, show only its current stage/status, document entry and review focus; ask for explicit approval or questions. Do not issue the next stage's continuation prompt before approval. Discussion and edits retain the stop; self-check and present revisions again.

After explicit approval, in one handling of the message: preserve the actual decision source and exact reviewed version; update approval, current run and next work together as appropriate; inspect the returned saved revision and view result (reread when uncertain); then report the saved outcome and next suggestion. Do not ask the user separately to approve saving or the prompt. If state saving failed, do not claim success; if state saved but the view failed, repair the view at that revision without replaying the approval. Only give the handoff entry once the save is confirmed.

After a user-visible work unit is saved, wait for explicit approval where document review is required, or for continuation where it is not. An approval may include “continue”; record it and proceed without a second confirmation. Approval without a continuation request leaves a saved boundary. Never treat “continue” alone as document approval. Ordinary continuation in this session needs no session permission; starting overall review after implementation still follows the explicit scope authorization above. Stage-internal work and authorized repair remain continuous; failures lead to repair/re-review rather than mechanical advancement. At final handoff do not invent a next-session task.

At a recommended session boundary or when the user requests continuation help, give current status, artifact and next suggestion, followed by one line in the saved delivery language using the actual absolute directory: “Use Aimship to continue delivery <actual directory>; first read the current state and relevant formal documents, then continue the recorded work.” In Chinese: “使用 Aimship 继续交付「实际目录」，先读取当前状态和相关正式文档再接续。” Do not output placeholders or long prompts at every stage. Full tasks, inputs, deliverable requirements, review stops and unresolved matters stay in existing state/formal documents/rules, not a new prompt or handoff file. A complete prompt may be generated when requested, without an arbitrary length limit.

In a new session, explicitly activate Aimship and uniquely resolve the same delivery from a trustworthy path/binding; if missing or ambiguous, request the directory or candidate selection, never a global latest delivery. Read the actual statePath returned by read, verify deliveryId when known, retain the saved language, reload fixed rules and current inputs, and inspect document approval versions, real artifacts and unfinished effects before choosing work. An old prompt or “continue next stage” is not approval. A draft remains pending across sessions. Stop the old writer before the new writer takes over. Aimship does not create sessions, use the clipboard, or launch an AI tool.

End when the current confirmed goal is met. For explicitly limited design work this means the agreed design. For development it includes agreed review and verification. “Show me the result” does not shorten the goal. If the user explicitly changes the endpoint, preserve the old goal, decision and unfinished work, update the arrangement, and assess the revised goal. An incomplete handoff is allowed but is not goal completion.

Small corrections within the original goal can reopen the same delivery: preserve its previous closure and result basis, increment the cycle, and review/verify affected work. A separate goal or substantial redesign starts a related delivery; retain the defect or source relationship without introducing parent/child scheduling. Prepared, accepted, merged and deployed are independent facts.

## Formal artifacts and generated status

Read [document patterns](document-patterns.md) when establishing or revising the arrangement. All new formal documents use its fixed outlines and [artifact map](artifact-map.json). Schema 5 / delivery protocol 3 uses ordinary Markdown and searchable business numbers. Preserve the saved language; do not translate original materials. State holds the control facts for batches, runs, reviews, verification coverage and acceptance. Submit domain operations through the current CLI, not replacement control arrays. status.md and the finite generated sections of plan/testing/review derive from those same facts. AI maintains approved definitions, explanations, detailed REV/RUN records and evidence; do not hand-maintain a second progress table. read/check/resume are read-only; inspect view and document-change warnings, and use explicit render to repair a stale/missing view. Preserve edits before rebuilding; never infer a business decision from hand-edited display text. After partial view failure use the saved revision, not a repeated business update.
