# Define requirements

## Inputs

Read the preserved original input, problem findings, adopted material and current decisions.

## Goal and scope

Establish the one current requirement authority, its acceptance criteria and the actual adopted or authored scope.

## Actions

Write the current requirements, important rules, normal/error/boundary behavior, constraints and observable acceptance criteria. Include context and scope, not just a checklist. Link sources; a complete applicable existing PRD is adopted directly without rewriting or renumbering. For partial adoption, write this iteration’s PRD with source, inclusions, exclusions and acceptance. For unchanged supplied input, use the actual delivery request as the adoption basis; no repeated source approval is required. Review AI-authored or substantively revised requirements, reusing evidenced current-content approval when available. Ask only concrete unresolved questions.

Ask for business behavior, compatibility or endpoint choices that cannot be inferred. Do not invent user acceptance.

Use the nine-chapter [PRD template](../templates/prd.md) for new/partial requirements: retain source correspondence, objects/states, uniquely defined behavior and permission/error rules, page operations and decidable AC. Fully adopted inputs retain their original format. Check every required field and distinguish unknown facts from inapplicable features.

For later edits, apply [in-place revision rules](../document-revisions.md); keep the same required fields and identities.

## Outputs and result

Use the selected PRD requirement entry. For a new PRD preserve the ordinary template headings and section order; a complete adopted PRD retains its own outline.

## Completion and stop

The requirements are adequate for the commissioned next work and material ambiguities affecting it are resolved. Reuse adequate requirements without claiming they were newly produced.

Self-check the selected outputs and stop for their [current-content review](../document-review.md); unchanged supplied inputs follow the shared adoption rules. Production done is separate from approval.
