# Define requirements

## Basis

Read the preserved original input, problem findings, adopted material and current decisions.

## Work and result

Write the current requirements, important rules, normal/error/boundary behavior, constraints and observable acceptance criteria. Include context and scope, not just a checklist. Link sources; external material is adopted through Scope rather than rewritten.

## Continue when

The requirements are adequate for the commissioned next work and material ambiguities affecting it are resolved. Reuse adequate requirements without claiming they were newly produced.

## Decisions and blockers

Ask for business behavior, compatibility or endpoint choices that cannot be inferred. Do not invent user acceptance.

Use [the shared core](../core.md) for state, evidence and continuation rules. Record meaningful results in an artifact or referenced section; a file alone is not completion.

## Artifact contract

Use the selected PRD/Scope requirement entry. Preserve the `requirements` section anchor (Scope uses adoption/goals as applicable). Follow [document patterns](../document-patterns.md) and the single [artifact map](../artifact-map.json). Keep this run independent even when its document is shared. New runs need a precise result location; adopted work is not a newly executed stage.

## Human document review

Apply [document review](../document-review.md): generate → self-check → present the concrete document entry, current review status and focus → wait. Record explicit user approval of this version/content, then follow the core session interaction: continue within the group, or suggest a new session at its boundary; continue here if requested. Questions or edit requests retain the stop; edits require self-check and re-review. Production `done` is separate from approval and final acceptance.
