# Review one document, then continue

The selected development order is requirements intake / PRD → technical design → interface contract and independent SQL when applicable → test cases → implementation plan → implementation with batch and overall review → independent verification → handoff and acceptance. Test design precedes planning in the standard delivery. An explicitly limited scope can omit cases/verification, but is a partial handoff, not standard complete delivery. Keep the agreed endpoint: prototype and investigation have their own reviewable outputs; design-only stops at the commissioned design. Review-only and verify-only use their existing object/case basis without inventing implementation or uncommissioned upstream stages. Frame clarifies inputs; requirements establishes the adopted input or approved AI-authored requirement authority. Do not generate empty stages or templates. When two responsibilities share the same already-approved current document, reuse that exact approval without asking twice.

Human review applies to AI-authored or substantively revised requirements, prototypes, independent diagnoses, technical designs, each interface/SQL document, test cases and implementation plans. It does not apply to unchanged user-supplied inputs or internal source, adoption, self-check and state records.

When the user supplies a complete applicable PRD/prototype and clearly asks to deliver from it, record the actual request as the adoption basis and register the unchanged document as mode input. Check its content and fit; do not invent an approved record or ask the user to approve the same source again. File presence alone is not adoption intent. If intent, scope or a conflict is genuinely unresolved, ask that specific question with its options and impact; use next.questionRef and a blocked current stage. Once answered, record the answer in the existing basis/work material and clear questionRef. No confirmation history or extra approval is needed. A partial-scope or substantively rewritten PRD is this delivery’s AI output and follows normal review.

For reviewable AI outputs (mode new, or mode reused for an existing reviewable output):

1. Write or revise the document while preserving its outline, identities and references. Self-check content, coverage, consistency and the actual entry. Keep work completion separate from self-check and user approval.
2. Save the self-check record for that version/content. Give the user the document link, a short summary of decisions and unresolved questions, current stage/review status and review focus. Do not give the next-stage continuation prompt while review is pending. Stop for human review. For several interface/SQL files, name and present each document individually; do not ask approval of an unspecified supporting package or introduce a scope-selection interface.
3. Record an explicit approval with its actual decision source and exact current document version/content. Existing approval of that same content may be recorded without asking again; check it rather than inferring from a file's presence. Save and inspect the result. Stop at the stage boundary; if the message also asks to continue, proceed without another confirmation. Within a multi-document stage, continue preparing the next applicable document after its prerequisite approval. Questions, silence, “continue” alone or “show me the results” are not approval.
4. Answer questions while retaining the stop. For requested edits, record `changes-requested`, revise, self-check and present again. Neither `done`, an existing file, nor an Agent review substitutes for user approval. A prior explicit decision may be recorded if it really identifies this exact content; never manufacture one from general implementation permission.

Do not ask human approval for every execution log, batch review or test result. Once the plan and required documents are approved, authorized implementation, Agent review, defect repairs within those requirements and retests can continue, showing results. New material decisions and production actions still need their own authorization. Final `outcome.acceptance` is a separate user decision; document approval does not accept the delivery, merge, deploy or execute SQL.

## State and evidence

New state has `reviewPolicy: 1` and append-only `reviewHistory`. Use the [CLI review protocol](../../../docs/cli.md#document-review-protocol) for exact fields. `read`, `check` and `resume` return current fingerprints and review status; state tools check records and dependencies, not user identity or authenticity. Preserve a concise, faithful decision excerpt with original conversation/message locator and date in a local evidence file or existing formal record. Do not label a synthetic test decision as a real user's approval. Keep decision evidence files immutable and add new decisions in new files. The source hash records submitted evidence bytes, not an authenticated signature; changed/missing evidence blocks release until reconciled.

For new plan/testing templates, approval covers content before the ordinary execution headings mapped to `execution`/`runs` respectively. Subsequent task execution and RUN/conclusion records belong in their later sections; moving changed design into result sections to evade review is forbidden. Other documents and reused formats use the whole registered file. For prototype assets and remotely adopted formats, preserve a readable local fixed-version review basis that identifies every relevant asset/version; report binary/remote inspection limits. Register local/repository linked assets in documents[].assetRefs to bind their bytes; the Agent must check that this set is complete. Do not claim entry-file hashing alone verifies all linked assets.

Stage runs use the agreed array order; by default a run depends on its predecessor. `dependsOn` can state explicit preceding dependencies for independent work, and declared input/output producer links plus earlier selected development prerequisites also apply. Record the reason for changing an arrangement. A pending AI-output review or unresolved input question holds dependent work; it does not authorize unrelated work outside the commission. `status.md` shows the current stage, pending document, review status and recorded next stage. While review is pending, chat presents only the current document/status and review focus; give the next-work suggestion after approval has been saved and checked. `resume` preserves the same stop and never automatically turns a question or old `done` into approval.

## Changes and old states

Use existing CHG records to explain semantic changes, affected requirements/documents/runs and the real decision source. Change the document version, keep old approvals and necessary old meaning/evidence, mark affected producer/dependent runs `needs-review`, and return to the corresponding document stage. An old approval cannot release new content. For a revised supplied input, record the actual updated adoption basis and check the new content without inventing approval; AI-authored or substantively rewritten outputs require renewed approval. Then recheck affected downstream work in dependency order and restore applicability with evidence; never clear every result or reset unaffected branches. Update `currentRun`/`next` to the actual re-review stop. Tools cannot infer all semantic dependencies: Agent impact analysis remains necessary.

For a formatting/typo-only adjustment to an approved output, self-check the new digest and append an `editorial` reconciliation that cites the previous approved digest and explains why meaning is unchanged. It carries the old approval without fabricating a new user decision. No full downstream re-review is needed. A changed requirement, case expectation or design choice is never editorial.
